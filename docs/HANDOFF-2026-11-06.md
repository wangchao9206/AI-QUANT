## 2. 接手时先准备什么

- 拉取仓库 `main`；必须包含基线提交 `8910780` 或其后续提交。
- 使用原有 Compose 项目名 `ai-quant`，保留原有 PostgreSQL 数据卷、行情缓存和本地配置。
- Docker Engine / Compose V2；镜像构建需能访问镜像仓库以及 Maven、npm、PyPI 依赖源。并行构建多个 Java 镜像可能占用较多内存，可逐个构建。
- 标准 Dockerfile 已包含构建工具。仅本机开发时才需另外安装 JDK 17、Maven 3.9、Node 22 和项目 Python 依赖；不建议沿用旧 Maven 3.5。
- `infrastructure/.env`、真实天勤账号、SMTP 凭据及数据库备份不在 Git 中，需由原维护者通过安全渠道交接。克隆仓库不会自动带回这些内容。
- `.test-tmp/` 中的备份、截图、临时构建目录和测试脚本也不在 Git 中，不应作为新机器部署的前置依赖。

以下命令均从**仓库根目录**执行，使用 PowerShell。先定义辅助函数，明确环境文件和项目名，任何一步失败都先处理原因，再继续：

```powershell
function Invoke-AiQuantCompose {
    docker compose --project-name ai-quant --env-file infrastructure/.env -f infrastructure/docker-compose.yml @args
    if ($LASTEXITCODE -ne 0) { throw 'ai-quant Compose 命令失败，请查看上方错误。' }
}
```

首次克隆使用：

```powershell
git clone https://github.com/wangchao9206/AI-QUANT.git
Set-Location AI-QUANT
git switch main
```

已有工作目录应先保存自己的修改，再使用 `git pull --ff-only origin main`。不要用覆盖工作区的方式更新。

## 3. 环境变量

首次部署才复制模板；已有 `.env` 原样保留，补充缺少的配置，不要覆盖：

```powershell
if (-not (Test-Path -LiteralPath 'infrastructure/.env')) {
    Copy-Item -LiteralPath 'infrastructure/.env.example' -Destination 'infrastructure/.env'
}
```

| 配置 | 要求 |
| --- | --- |
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | 已有环境与实际数据库一致。修改环境文件不会自动修改已有数据库角色的密码。 |
| `IDENTITY_INTERNAL_SECRET` | 至少 32 个随机字符；所有相关 Java 服务和 algorithm-service 必须一致。Compose 已传递到两类服务，不能只给 Java 配置。已有环境保留原值。 |
| `PUBLIC_APP_URL` | 浏览器真实访问地址，也是验证／重置邮件链接的地址；本机默认 `http://localhost:8088`。 |
| `AUTH_COOKIE_SECURE` | 本机 HTTP 为 `false`；HTTPS 对外部署应为 `true`。HTTP 下设为 true 会导致浏览器不能正常携带登录 Cookie。 |
| `MARKET_DATA_PROVIDER` | 完整实时期货、期权和盘口功能使用 `tqsdk`。 |
| `TQSDK_USERNAME` / `TQSDK_PASSWORD` | 有相应国内期货、期权及历史数据权限的真实账号。无权限时显示不可用／预热状态，不生成替代行情。 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD` / `SMTP_FROM` | 真实发信配置。587 通常使用 STARTTLS；465 使用 SSL 时关闭 STARTTLS，具体按服务商要求。 |
| `SMTP_AUTH` / `SMTP_STARTTLS` / `SMTP_SSL` | 模板默认 true / true / false。未配置 SMTP 时管理员仍能登录管理，但不能完成真实邮箱注册与找回流程。 |
| `FRONTEND_PORT` / `GATEWAY_PORT` | 默认 8088 / 18080。前端对外开放，网关默认仅绑定本机。 |
| `NACOS_ENABLED`、`NACOS_AUTH_*`、`NACOS_USERNAME/PASSWORD` | 按实际环境保留；模板值不是正式凭据。服务发现与 Nacos 自身鉴权是不同配置，不要只为了消除提示随意开启。 |

新环境生成随机内部密钥的方法如下；将结果仅写入本地 `.env` 或密钥管理系统，不提交到 Git：

```powershell
$identityBytes = New-Object byte[] 32
$identityRng = [Security.Cryptography.RandomNumberGenerator]::Create()
$identityRng.GetBytes($identityBytes)
$identityRng.Dispose()
[Convert]::ToBase64String($identityBytes)
```

Compose 已配置 `market-service -> IDENTITY_SERVICE_URL=http://identity-service:8085`。改用独立容器平台时也要保留这一连接，用于后台监控每轮重新校验执行者权限。

更换域名／端口时，一并核对身份服务和 Gateway 的 `CORS_ALLOWED_ORIGINS`；只修改 `PUBLIC_APP_URL` 不会自动修改所有 CORS 配置。反向代理应将 `/api/` 转发到 Gateway，并保留 SPA 路由回退；不要把算法、身份或数据库内部端口直接公开。

## 5. 构建与启动顺序

标准构建直接使用仓库 Dockerfile，不依赖原机器 Maven 缓存目录或 `.test-tmp` 里的临时运行镜像：

```powershell
# 此步骤只构建镜像，不启动应用或执行数据库迁移。
$env:COMPOSE_PARALLEL_LIMIT = '1'
Invoke-AiQuantCompose build identity-service algorithm-service market-service strategy-service paper-trading-service chanlun-service gateway-service frontend
Invoke-AiQuantCompose build chanlun-native-worker chanpy-worker czsc-worker chanlun-baseline-worker
```

然后按依赖顺序恢复／启动。`up` 会自动启动各服务在 Compose 中声明的依赖：

```powershell
Invoke-AiQuantCompose up -d --wait --wait-timeout 300 postgres
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 identity-service algorithm-service
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 market-service
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 strategy-service paper-trading-service
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 chanlun-service
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 gateway-service
Invoke-AiQuantCompose up -d --no-build --wait --wait-timeout 300 frontend
Invoke-AiQuantCompose up -d prometheus
```

启动过程中会用到 PgBouncer、Redis、Nacos、RocketMQ 及初始化任务。`rocketmq-volume-init`、`rocketmq-topic-init` 是一次性任务，成功后显示 `Exited (0)` 正常；常驻服务则应为 Running／Healthy。镜像下载和首次启动可能超过示例等待时间，应查看日志判断，而不是反复重建数据卷。

首次部署整个仓库且环境已配置好时，也可直接 `Invoke-AiQuantCompose up -d --build`，再按下一节核对状态。已有环境推荐上面的分步方式，便于定位迁移与启动失败。

**如果唯一变化只是最新中文名称前端代码，且后台已是本次功能版本，只需构建和重建 frontend；不需要数据库迁移：**

```powershell
Invoke-AiQuantCompose build frontend
Invoke-AiQuantCompose up -d --no-deps --no-build --wait --wait-timeout 180 frontend
```

这条增量命令要求原 Gateway 及后端已经在运行；用户当前停止 Docker 的机器，仍需先恢复后端。不要使用 `docker compose start` 来代替代码升级，它只启动已有容器，不会应用新镜像与新增环境变量。

## 6. 数据库迁移说明

Flyway 在对应 Java 服务启动时自动执行，不需要人工把 SQL 文件逐个导入：

| Schema | 本次相关版本 | 作用 |
| --- | --- | --- |
| `identity` | V1、V2、V3 | 账号／租户、独立管理后台、实盘看盘菜单。 |
| `paper_trading` | V8 | 模拟交易及相关私有记录租户隔离。 |

| `market` | V2 | 后台监控任务、触发事件、配置审计及 FORCE RLS。 |

已有记录默认归入租户 `00000000-0000-0000-0000-000000000001`；新租户不应看到其他租户私有记录。此前部署时保留过 17 个模拟交易会话，该数量只是历史验收快照，不应当作未来固定数量。

迁移账号需要创建／授权 `aiquant_tenant` 数据库角色的权限。HTTP 私有请求使用事务局部角色与租户变量，依赖现有 FORCE RLS。不要通过关闭 RLS、删除 schema、删除 Flyway 历史或随意 `repair` 绕过报错。SaaS 正式环境后续应进一步分离迁移、后台工作线程与 HTTP 运行数据库凭据。

## 7. 接手者部署后如何确认

以下是待接手者执行的验收步骤，不是本次新运行的检查：

```powershell
Invoke-AiQuantCompose ps -a
Invoke-AiQuantCompose logs --tail 100 identity-service market-service algorithm-service gateway-service frontend
```

1. 打开 `http://localhost:8088`，已有账号使用当前密码；新数据库的 admin 首次登录后改密。
2. 主系统可以打开 `/options`、`/live`，管理员通过顶部按钮进入独立 `/admin`。无权限账号不能仅通过输入地址绕过后台授权。
3. 期货／期权显示中文主名称；选择后实际请求仍是原始合约代码。中文补全依赖 `instrumentNames.ts` 和实时目录，不要把中文名称写回 symbol 或接口参数。
4. 实盘看盘检查九周期与五条均线。历史不足 180 根时 MA180 显示“—”正常，尤其是新交割月的月线。
5. 期权目录首次加载可能预热；休市 `CACHED`／`STALE` 正常。没有对应交割月期权时应显示空状态，不能替换成其他月份或伪造盘口。
6. 在测试租户建立监控，确认检查时点更新、配置可保存、暂停和恢复生效；关闭浏览器后服务仍运行。停止 Docker／主机休眠时监控不会运行，重启恢复时不补发旧行情触发。
7. 启用真实 SMTP 后，使用测试邮箱实际完成注册验证、改密、找回和邮箱绑定；仅通过本地 SMTP 协议测试不能证明外部邮件送达。
8. 使用不同租户确认模拟账户、监控、触发与审计隔离，原有业务数据保留；不要用正式租户创建大量验收任务。

历史验收：最终中文改动的前端 64 个文件、357 项测试通过，类型检查和本地生产构建通过；隔离桌面／390px 手机界面验证中文名称和无整页横向溢出。后台阶段还验证过真实 PostgreSQL RLS、租约、暂停竞态、事件去重／事务回滚、撤权及关闭浏览器后的持续记录。具体证据见本文末尾的阶段记录。以上不替代接手机器的连通性与权限验收。

行情服务正常启动后可按需执行历史数据命令；这些命令会采集或更新数据，不是启动服务的必需步骤：

```powershell
# 查看已有主连历史；不会主动执行全量下载。
Invoke-AiQuantCompose exec -T algorithm-service python scripts/download_history.py --status

# 按需同步指定品种主连历史。
Invoke-AiQuantCompose exec -T algorithm-service python scripts/download_history.py --symbols CJ0,RB0,M0
```

## 9. 监控口径、限制与尚未完成的接入

- 页面显示周期与技术监控周期分开；技术监控当前支持 1／3／5／15 分钟。23 种条件、默认阈值及计算方式见 [后台监控说明](live-monitoring.md)。
- 技术信号只用已确认收盘柱；MACD 背离默认右侧 2 根完整柱确认。60 秒涨跌需要观察窗口；过时、断线、缓存与首次预热不会补发历史事件。
- “大额买／卖向成交增量”按 Tick 增量及价格相对买卖一估算，不是逐笔委托身份或主力资金识别。功能不下实盘订单。
- 主连创建监控后固定到实际交割合约，不自动换月；到期期权任务自动停用。执行者为最后保存／启用者，每轮重新核验当前账号、租户和读写权限。
- 默认每租户最多 20 个启用任务，全局 32 个，后台并发 4 个；一般每次完成后至少间隔 3 秒，并非交易所逐 Tick 推送保证。期权盘口 32 个合约、K 线 48 组订阅上限。
- 事件、操作与授权日志目前没有自动清理策略，应由维护者确定保留与备份期限。
- SMTP 服务商尚未配置，真实外部送达需接手后验证。当前 SaaS 能力是账号／租户／权限和 REST API 密钥，尚未实现 OIDC/OAuth、SAML、SCIM、订阅计费或平台专属适配器。
- 前次部署日志中存在 RocketMQ 行情广播发送超时。后台盘口监控有独立调度并直接读取算法接口，不依赖该广播；接手者仍应单独排查广播链路，不能把容器健康等同于消息已送达。

## 10. 常见问题与回滚

| 现象 | 优先排查 |
| --- | --- |
| Compose 提示内部密钥未设置／服务拒绝启动 | `.env` 是否存在、是否指定正确文件、密钥长度及两类服务的注入是否一致；无需输出密钥排查。 |
| 登录后仍返回 401／403 | 初始改密状态、用户与租户是否启用、成员权限、Cookie Secure 与实际 HTTP/HTTPS、CSRF、域名与 CORS、各服务时钟。 |
| 邮箱注册或找回失败 | SMTP 主机／端口／TLS 模式、账号授权码、发件地址及服务商拒信日志；不能改成模拟验证绕过。 |
| 监控 `FORBIDDEN` | 最后保存者的账号、租户成员关系及对应 market/options 读写权限。 |
| 监控 `STALE`／期权目录预热 | 交易时间、网络、真实行情权限、源时点；休市与刚启动时可以是正常状态。 |
| 无真实盘口／均线为空 | 档位或历史确实缺失；先确认数据权限和历史长度，不补造报价／均线。 |
| 迁移失败／RLS 拒绝 | 数据库凭据、schema、Flyway 日志、角色授权及迁移前置版本；不要删除业务数据解决。 |
| 构建慢或启动超时 | 依赖下载网络、镜像源、主机资源，逐个构建与查看失败服务日志；不要删除数据卷重试。 |

回滚时，停止受影响的应用，先确认旧镜像与现有数据库兼容，再把保存的镜像重新标为 `latest`，通过 `up -d --no-build` 重建对应服务。纯中文显示更新只需回退 frontend。

**回退镜像不会回退数据库迁移。** 本次包含身份、租户隔离和监控表迁移，不应盲目降回不理解租户边界的旧版本。若确实需要恢复数据库，应另行安排停写、保留当前完整备份并评估备份后新增记录，不能把覆盖恢复当作普通重启步骤。不要执行 `down -v`、卷清理或删除 Flyway 表来“重新部署”。
